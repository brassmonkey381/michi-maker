# Audit backlog

The full audit spec, 402 checks across 9 areas, each one adversarially reviewed by a second pass
that was told to refute rather than approve. This is the SOURCE for `qa/suites/`, not a substitute:
a row here is a check somebody still has to write.

`SPEC.md` is the opposite document. It is generated from the checks that actually run, so it can
never overstate coverage. Read that one to know what is tested; read this one to know what is not.

## How to read a verdict

The review pass gave every row one of six verdicts. Anything other than `ok` is a row that must be
fixed before it is built, and the reason is printed with it. Those are worth more than the clean
rows: a check built on a wrong expectation makes a green suite meaningless.

| verdict | meaning |
| --- | --- |
| `ok` | the expectation was verified against the code |
| `wrong-expectation` | the author guessed and the guess was wrong |
| `not-observable` | the signal does not exist in the DOM or the network today |
| `unsafe` | running it could cause real harm |
| `duplicate` | already covered by another row |
| `vague` | too loose for an automation to decide |

## new-user-flow

**Preconditions.** Every NEW check runs in a FRESH browser context with its own profile directory and empty storage for the origin under test, because three separate gates are keyed on per-browser state: `michi.landing.seen`, `tcgscan_landing_seen`, and `tcgscan.binderTaste.v1.<uid>` (monotonic, never decreases, a reused profile starts at the wall). Guest lanes seed NOTHING and let the app mint its own anonymous Supabase session; free lanes seed `sb-piikwvntldytjejxmcla-auth-token` with a password-grant session per ORIGIN (michi-maker.com and tcgscan.ai are separate origins and need separate seeds) for a throwaway account created through POST /auth/v1/admin/users with {email_confirm:true} and an email prefixed `michi-uitest-` / `michi-flowtest-`, so michi-maker/scripts/_purge-test-accounts.mjs can sweep it; every run MUST call that purge in a finally and MUST fail loudly when survivors remain (two binders named "uitest one" once reached the live Discover feed). A michi free fixture needs a username already claimed, or UsernameGate covers every route and invalidates every other assertion in the run. Both sites must be reached at their production origins for the serverless and rewrite rows (targets prod): a local static export resolves bracketed filenames and returns 200 for exactly the paths that 404 on tcgscan.ai, and michi's /api/* routes do not exist locally at all. Before asserting anything tier-shaped, wait for the tier to settle (the entitlements read has resolved, or the plan table has left its foot placeholder); both apps report guest until it lands. Billing safety is a hard precondition: block `**/functions/v1/stripe-checkout` at the route level and refuse to click any control whose accessible name starts with "Pay $", and never press "Start free 3-day PRO trial" outside a disposable account, since a trial is one per account forever. Known network noise to allow-list by exact URL rather than by keyword: /fonts/*.woff2 on tcgscan.ai, and POST /rpc/card_alternates returning 400. Tag every run with ?utm_source=qa-studio so its analytics_events and analytics_sessions rows can be excluded from the analytics-studio funnels; each guest lane permanently adds one anonymous row to auth.users that no existing sweeper can reach.

**Review pass.** Forty-five rows, verified against the repos rather than the map. Five are wrong and must not ship as written; the other forty are sound, and several (NEW-033, NEW-038, NEW-041, NEW-013) are the strongest rows I have seen in this programme because they pin behaviour to code that genuinely has no other observable.

The five refutations. NEW-021 asserts uppercase usernames are refused: both call sites lowercase before validating (AuthSheet.tsx:119, store/auth.tsx:437), so they are accepted, and a taken name does not error in the sheet at all, because createWithUsername calls onClose() unconditionally and hands off to UsernameGate after the account already exists. NEW-024 quotes the confirmation string from run() (AuthSheet.tsx:101), but a create submit takes createWithUsername, which sets a different string at :147. NEW-034 applies the PlanComparison closed-checkout note to every purchase CTA; OfferCards has its own note and its own button suffix. NEW-035 is the worst of the five: it tells the suite to grep the bundle for 'TCGScan', which ships in the bundle by construction (changelog.ts:38-41 alone guarantees a hit), and /whats-new hides the product filter with display:none rather than omitting it, so the string is in the DOM too. NEW-044 claims campaign params survive the landing hop on both apps; on tcgscan the hop is window.location.replace to a static page, so they are lost on precisely the fresh-context guest runs the section cares about.

That last one is not a row-level defect, it is a hole in the preconditions. The whole section proposes ?utm_source=qa-studio as the mechanism that keeps QA rows out of the analytics-studio funnels, and on tcgscan that tag does not arrive unless the lane seeds tcgscan_landing_seen first. Fix it in the preconditions, not in NEW-044.

One correction outside the verdicts because it changes how a failure is read: NEW-001's note says the tcgscan landing redirect is skipped when localStorage throws. There is no try/catch at _layout.tsx:41-47, so a blocked-storage context throws at module scope and the app does not mount at all. A blank body there is BROKEN, not a false FAIL, and it is the opposite of michi, which genuinely fails open at landing.ts:16-21.

The section's real structural weakness is that its riskiest instructions live in row notes instead of the preconditions: the BLOCKED-not-FAIL rule for UsernameGate, the VOID-not-FAIL rule for the post-upgrade token window, the prompt-queue drain before any michi signed-in assertion, and the never-sign-out-on-michi-while-a-lane-holds-the-account rule. All four are correct and all four are invisible to a runner that reads only the check list.

What it is missing, in order: tcgscan's email-code sign-up is untested end to end; the no-session state (anonymous sign-in refused or rate-limited) has no row and will read as a false FAIL on NEW-008 the first time GoTrue throttles a run; nothing establishes what a brand-new account actually starts with, yet four cap rows assume a fixture already at its cap and will score PASS when the gate simply never fires; campaign-tag survival needs its own row; and the run never counts the anonymous auth.users rows it permanently creates, which is the one irreversible cost the section admits to and then does not measure.

### Fix before building

- **`NEW-021` (wrong-expectation)** Two of the three sub-assertions are false. (a) UPPERCASE IS NOT REFUSED. Both AuthSheet.tsx:119 and store/auth.tsx:437 call .trim().toLowerCase() BEFORE testing /^[a-z0-9_]{3,20}$/, so 'MyName' normalises to 'myname' and is accepted. Only length and punctuation can fail. (b) A TAKEN NAME IS NOT SHOWN IN THE SHEET ON THE CREATE PATH. createWithUsername (AuthSheet.tsx:130-158) creates the account first, then calls claimUsername, then runs `if (c.error) setError(c.error); onClose();` unconditionally, so the sheet CLOSES and the app-wide UsernameGate takes over (this is deliberate, per the comment at :127-129). (c) The reserved string is not fixed: reservedMessage (store/auth.tsx:127-135) returns 'That username is reserved for someone else. Try another.', 'That username is too close to michi-maker’s own name. Try another.' or the generic form, depending on check.detail.
  - correction: Rewrite as: 'Submit a name that is too short or carries punctuation and the sheet shows Pick a username: 3–20 characters, lowercase letters, numbers, or underscores. (AuthSheet.tsx:121). Submit MixedCase and it is accepted, normalised to lowercase. Submit a name known to be taken and the account is STILL CREATED; the sheet closes and UsernameGate opens instead with the claim error (so this row hands off to NEW-028/029, it does not assert in-sheet). A POST to /rest/v1/rpc/username_available fires inside claimUsername.' Note the account-created-anyway behaviour raises the write budget: a taken-name run burns a real account even though the user never got their name.

## Critics

**Verdict.** The spec sheet is strong and unusually well grounded; the package's problem is that the three things the owner asked for by name are the three it currently cannot do. The shipped rig has 66 checks in three areas and exactly two personas (guest, free), so the guest -> free -> pro-trial ladder is unrunnable, the "databases identical across tiers" question has no valid check in any section (every attempt measures virtualized tile counts), and the new 3-binder-page cap is only ever read from localStorage, never enforced by a real submit.
